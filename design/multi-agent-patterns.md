# 多 Agent 协调模式

> 整理自 Anthropic 官方文章《Multi-Agent Coordination Patterns》

## 五种模式总览

| 模式 | 拓扑 | 适用场景 |
|---|---|---|
| 生成器-验证器 | 两节点循环 | 对质量要求严格、有明确评估标准的输出 |
| 编排器-子智能体 | 星形，中心化 | 清晰的任务分解，子任务短小且有明确边界 |
| 智能体团队 | 星形，工作者有状态 | 并行、独立的长时间运行子任务 |
| 消息总线 | 事件网络，有路由器 | 事件驱动流水线，不断增长的 Agent 生态 |
| 共享状态 | 去中心化，无路由 | 协作研究，Agent 需要基于彼此发现进行构建 |

---

## 模式一：生成器-验证器

**工作原理**：生成器产出初始结果 → 验证器按明确标准评估 → 不通过则带具体反馈退回生成器 → 循环直到通过或达到最大迭代次数。

**适用场景**：代码生成（一个 Agent 写代码，另一个写并运行测试）、事实核查、合规验证。错误输出的代价高于额外生成周期时使用。

**局限**：
- 验证器质量取决于标准的质量，标准模糊则形同虚设
- 迭代可能振荡不收敛，需要设置最大次数和回退策略

---

## 模式二：编排器-子智能体

**工作原理**：编排器接收任务、制定计划、分派子任务给子智能体。子智能体完成后返回结果并终止，编排器综合输出。编排器可以自己处理部分子任务，同时将其他任务并行分派出去。

**适用场景**：任务分解清晰，子任务之间相互依赖性最小。Claude Code 使用这种模式：主 Agent 自己写代码，在需要搜索大型代码库时在后台派遣子 Agent。

**局限**：
- 编排器是信息瓶颈，子 Agent 之间的关联发现必须经编排器路由，细节容易丢失
- 除非显式并行化，否则子 Agent 顺序执行，承担了多 Agent 的 token 成本却没有速度收益

> **这是当前项目已实现的模式（Coordinator + SubAgentTool）。**

---

## 模式三：智能体团队

**工作原理**：协调器生成多个工作 Agent 作为独立进程。团队成员从共享队列中认领任务，跨多个步骤自主工作，完成后发出信号。

**与编排器-子智能体的核心区别**：工作者的持久性。子智能体完成有边界的子任务后终止；团队成员**跨多个任务保持活跃**，积累领域上下文和专业知识，随时间提高性能。

**适用场景**：大型代码库框架迁移——每个团队成员对其分配的服务建立真正的熟悉度（依赖图、测试模式、部署配置），这种积累的上下文是一次性分派无法复制的。

**局限**：
- 独立性是关键要求，团队成员无法轻易共享中间发现
- 完成检测更困难，协调器需要处理部分完成的情况
- 多个成员操作同一资源时需要仔细的任务分区和冲突解决

---

## 模式四：消息总线

**工作原理**：Agent 通过发布和订阅事件交互。Agent 订阅关心的主题，路由器传递匹配的消息。新 Agent 加入时只需声明订阅，无需修改现有连接。

**适用场景**：安全运营自动化——告警从多个来源到达，分诊 Agent 分类后路由给专门的调查 Agent，调查结果流向响应协调 Agent。工作流由事件产生且可能随发现动态变化。

**局限**：
- 追踪困难，事件级联跨越多个 Agent 时调试复杂
- 路由准确性至关重要，错误分类会导致系统静默失败

---

## 模式五：共享状态

**工作原理**：没有中央协调器。Agent 自主运行，从共享数据库、文件系统或文档中读取和写入。Agent 检查已有发现、采取行动、将结果写回。工作在初始化时填充存储后开始，在满足终止条件时结束。

**适用场景**：研究综合系统——多个 Agent 调查复杂问题的不同方面，学术文献 Agent 的发现可以立即被行业报告 Agent 看到并影响其调查方向。发现需要实时在 Agent 之间流动。

**局限**：
- 没有明确协调，Agent 可能重复工作或采取矛盾方法
- 反应循环风险：Agent A 写发现 → Agent B 写后续 → Agent A 再回应，无限消耗 token
- 终止条件必须作为一等设计考量，而非事后考虑

---

## 模式选择决策

**编排器-子智能体 vs 智能体团队**：工作者需要维护上下文多长时间？
- 子任务短小、产生明确输出 → 编排器-子智能体
- 子任务需要跨调用积累上下文 → 智能体团队

**编排器-子智能体 vs 消息总线**：工作流结构是否预先已知？
- 步骤序列固定 → 编排器-子智能体
- 工作流由事件产生、可能动态变化 → 消息总线

**智能体团队 vs 共享状态**：Agent 是否需要彼此的发现？
- 在独立分区上工作、最后合并 → 智能体团队
- 发现需要实时在 Agent 之间流动 → 共享状态

**消息总线 vs 共享状态**：工作是离散事件还是积累知识？
- 逐阶段处理事件 → 消息总线
- 随时间基于积累发现构建 → 共享状态

---

## 入门建议

生产系统通常组合多种模式。对整体工作流用编排器-子智能体，对高度协作的子任务用共享状态；或用消息总线做事件路由，同时用智能体团队风格的工作者处理每类事件。

**大多数场景从编排器-子智能体开始**，以最小协调开销处理最广泛的问题范围，观察其局限性后再向其他模式演进。
